# RADE window design

Status: the one place for the RADE window's UI decisions (the Administrator, 2026-11-14: consolidate them). The window is the "One thing" design (the Administrator, 2026-11-14, [DECISIONS.md](DECISIONS.md)); it replaced layout B, layout A, layout P1 and the UI pass 3 proposals. Built in [engine/rade_build.py](../engine/rade_build.py) (from engine-v11 the window code is in [engine/ps/09-start.ps1](../engine/ps/09-start.ps1), [engine/ps/10-window.ps1](../engine/ps/10-window.ps1) and [engine/ps/window](../engine/ps/window)) (WinForms drawn in code, Windows PowerShell 5.1); the window code is the part from `function Get-AppFact` to the text-mode block. **Not verified on a device**: its logic runs in [tests/engine_test.sh](../tests/engine_test.sh) (section "window") against stand-in types; its layout is measured on the real Windows Forms by the Windows job and by the layout self-check ("Proof" below); a round on a work computer is the last proof.

Mockups: https://claude.ai/artifact/M2EKZCrkUtYshuFGq746Ld, pages "Redesign: One thing (14 Nov)" and "Polish pass (15 Nov)" (sizes, states, text lengths and each corrected part, before and after; the Administrator, 2026-11-15). How the three concepts compared: [reviews/2026-11-14-window-redesign-proposals.md](reviews/2026-11-14-window-redesign-proposals.md). Sources of older rows: RADE = [docs/DECISIONS.md](DECISIONS.md); Z = [rhope-ops/90-161.Z docs/DECISIONS.md](https://github.com/rhope-ops/90-161.Z/blob/main/docs/DECISIONS.md).

## The idea

The window shows one statement or one question at a time (a "card"). It is quiet when things are fine and speaks only when it needs the person. Everything else is one key away, in the Record (F2). Each answer moves on: there is no Next / Back row and no Exit button.

## Sizes

One place in the engine: `$ui.Z` (pixels at 100 % scaling). The [RADE page](../index.html) uses the same button size and gap (the Administrator, 2026-11-15). Text scales with the controls (R28; the Administrator, 2026-11-17): on the R25 device the form scaled 1.5 x (autoScale 144) while text stayed at 96 dpi (font 18 px), so text looked small. RADE keeps one scale source for the controls, and asks Windows for the real dpi before any form exists (a native call from user32, `SetProcessDPIAware`, in the engine; it changes nothing when the process already has an awareness, and without it, for example in Constrained Language Mode, the window runs as before). Every font is then made as much bigger as the controls are: a probe font of 100 pt shows the dpi the screen draws text at, and `$ui.FontK` = the controls' scale over that (steps of 0.25; 1 where Windows scales both; 1.5 on the R25 device). `AutoScaleMode Font` was not taken: it scales by the form font, which is the part that stays at 96 dpi there. The SCALE line prints `fontScale` and `ctlScale`. R34 (the Administrator, 2026-11-19): in PowerShell ISE the window read 96 dpi on a 150 % screen and the console drew it smaller and sharper; so RADE also reads the dpi awareness of its own thread (Windows 10 1607 or later) and, only when it is "unaware", makes that thread "system aware" before the form exists, and sets the old value back when the window closes or fails. The SCALE line prints `thread=` (`unaware`, `system`, `permonitor`, `unaware>system` when RADE changed it, or `n/a`) and `sysDpi=`; a device round proves the change. One scale source (R24): the window's parts are made at 100 % and Windows Forms scales them with the form; every size RADE sets or draws after that (the choices, the Record's list and step boxes, margins set per card, box widths, bars, scroll steps) goes through `$ui.Sc`, which uses the dpi the form scales to (its auto-scale dimensions). The screen dpi (`Graphics.DpiX`) is only reported: on the R24 device it said 96 while the form scaled 1.5 x. A button grows with its text and shrinks back for the next card (AutoSize, grow and shrink; R24: a long answer choice kept three buttons wide on Done).

Alignment (the Administrator, 2026-11-15, after the R24 pictures; [DECISIONS.md](DECISIONS.md)):

- **A label above its box** (R31 L3, the Administrator, 2026-11-19). The box of a text answer ("Your answer": a text question, and the last card of a test round) is under its label, 4 px apart, starts on the card's edge and is as wide as the card's text (from the edge to the end of the text column). The other label-box rows stay on one line (a choice of the agent: the brief names "Your answer").
- **One midpoint per row.** The RADE row (logo, the title column), the application row (its logo, its name) and each label-box-button row (the hand step's "Address", the site card's "Site address", the install card's "RADE shortcut in", the test extras) share one vertical midpoint: each part's top margin comes from the tallest part. A row that wraps (the test extras in a small window) is aligned line by line. A one-line box is a frame exactly as tall as the compact button beside it (measured, so one value drives both) with RADE's own 1 px edge; the text box inside fills the frame less 6 px on each side and sits in its middle. Label to box and box to button are 8 apart. The It-failed card's error box has no label or button beside it.
- **One left edge per card.** Where the ink starts (the text of the line in capitals, the headline or the tick on Done, the body, the row labels, the first link, the help and last lines) and the edge of the first button, the first choice and the error box are on one edge, 10 px into the card's column. Each part's ink start is measured on Windows (the part drawn into a bitmap: its own text flags, padding and the first letter's side bearing) and its margin moves it there (`$ui.Ink`, `$ui.FitEdges`). In the numbered list of a hand step the ink of the widest number is on the edge (shorter numbers are right-aligned to it); the closing line, the unnumbered lines and the buttons are on the same edge.
- **One border.** Every button (action, compact, link) draws its own face, its 1 px edge and its text in every state (normal, under the pointer, pressed, focused, default, not available), over what Windows drew: no theme border, no black default-button border, no dotted focus rectangle. A choice on Choose draws a 1 px gray edge, and 2 px navy when it has the focus. Focus is the 2 px navy ring the parent draws. Check boxes and the multi-line boxes (the error text, the Record's log) keep the Windows look.
- **Question headline** (the Administrator, 2026-11-15: rework B). The prompt's first sentence (up to the first "?", "." or ":" followed by a space or the end) is the headline at 22 pt; the rest is a body line under it; a one-sentence prompt has no body line. A first sentence too long for one line shrinks to fit: in 0.5 pt steps to 60 % (13.2 pt; never under the body size, 12 pt), and only at that size does it wrap (a choice of the orchestrator). It fits again when the window changes size. At 13.2 pt about 62 characters fit on one line in the smallest window (811 x 469) and about 81 at 1020 x 760. Other cards keep the headline size.

## Text lengths

The most characters of each text an application gives the window. Source of the numbers: `TEXT_LIMITS` in [engine/rade_build.py](../engine/rade_build.py) (a test keeps this table equal to it). They come from the real font, measured in the window by the Windows job (Segoe UI 10 pt = 6.8 px for each letter, 22 pt semibold = 14.9; the body size, 12 pt, is 6.8 x 1.2 = 8.2, derived by scaling, not yet measured: the Windows job's MEASURE lines give the real value), and the narrowest card (604 px). At 12 pt about 73 letters fit on a line of that card; a numbered guide line has a text column about 40 px narrower (the number and the gap), so 100 characters take 2 lines. In this release a longer text is a WARNING line of the build and a note of the app check (`scripts/check_apps.py`), not a failure (the Administrator, 2026-11-15); the window never cuts a part off, whatever the length.

| Text (manifest) | Limit | When longer, the window |
|---|---|---|
| application name | 48 | ends it with "..." on Choose and in the logo block; wraps it in a sentence |
| version | 14 | ends it with "..." |
| summary | 150 | wraps it to 2 lines on Choose, then "..." |
| step name | 56 | wraps it as the sentence of a hand step and in the Record; in the step line the bar goes to the next line |
| step title | 56 | The manifest field `title`: shown where the step name is shown to a person (the hand step's headline, the step line, the Record's step boxes); wraps as the name does. The log, the report, the summary and the results keep the name |
| step note | 200 | wraps it in the Record (the step list scrolls) |
| guide line | 100 | wraps it, in the text column of the numbered list |
| guide lines | 10 | A count: the numbered lines of one guide (a line that starts with a number and a full stop, "Cards"). More is a WARNING of the build, not a failure; the card then scrolls above its buttons in a small window |
| doneText | 24 | the button grows with the text and the row wraps |
| step doing | 80 | The manifest field `doing`: what the step does, in the present tense, on the now-doing line of the Run card ("Cards"); wraps it |
| step help | 160 | wraps it |
| answer prompt | 120 | wraps it as the sentence of its question card. A hard limit: a longer prompt stops the build and the schema check |
| answer choice | 40 | the button grows with the text and the row wraps. A hard limit, as the prompt |

RADE's own texts follow the same rule: a text the window draws wraps to 2 lines at most and then ends with "...", or its row wraps.
