## RADE and the app

Decided by the Administrator, 2026-11-14. RADE owns the computer and the run. The app owns the product and the site. RADE may know a platform (SharePoint, Power Automate, Word, Outlook), never an app's objects (a list, column, flow or setting by name). Test for any line of code or text: would it be the same for a different app? If yes, it is RADE's.

| Subject | RADE | The selected app |
|---|---|---|
| Window, screens, bars, log, report | Owns all of it | Supplies its name, summary, step notes and help text |
| Checks | Runs them; owns the check library | Declares which checks each step needs (`needs`) |
| Files on the computer | Makes folders, writes and downloads files, verifies sha256, recycles old files | Declares the files and the clean-up patterns |
| Order and gating | Runs steps in manifest order, applies `after`, blocks on a failed check | The author sets the order and the dependencies |
| What is created on the site or in Power Automate | Creates nothing of its own there | Declares or scripts every list, column, permission, flow and setting |
| Steps done by hand | Opens the address, shows the numbered steps, waits for Done or It failed | Writes the guide text; owns what the user imports |
| Values asked from the user | Asks what the install needs (site address), passes it once (`RADE_SITE`) | Asks its own settings in its own setup screen |
| Record of the install | Keeps the version, each step's state and the made list | Prints `PASS`, `FAIL` and `MADE` lines; each script is safe to run again |
| App data (rows, files, backups) | May read and write it inside DoD365 where a run type needs it (Diagnose, Restore, backup); how is not decided | Owns it; declares what RADE may touch |
| Starting the app | After its checks pass, a Start button opens the installed app from its local copy (no download); one shortcut opens RADE, in the folder the install card asks for (the Desktop folder at first; R29 N8) (the Administrator, 2026-11-17) | Supplies its start script (manifest `start`, a path in its local folder) and its own window |
| After the install | Not present; the app works if RADE is deleted | Flows, the Power App, health and its own alerts |
| Help | Names the Teams channel | Says what to do when one of its steps needs review |

Hard rule (the Administrator, 2026-11-14): users cannot write data across the DoD365 boundary through any of the Administrator's apps, RADE included. Inside DoD365 (the site, the user's OneDrive) RADE may read and write. The first version of the two rows above said RADE never writes to the site or touches app data; that was agent wording and is replaced.

No reconnaissance (the Administrator, 2026-11-14; cannot be changed): RADE, every app, every step, flow and test, and every agent that writes them, must never do anything that is malicious in nature or that could be misconstrued as malicious. Never, with no exception: finding or pinging hosts on the network, port checks, or working out network or logical boundaries by probing. Allowed: reading SharePoint and Power Platform data with the user's own account, in the open (the script says what it reads before it runs), including to record what that account can do so an app can be deployed. If there is any doubt, stop and seek approval from the owner before the code is written or run.

Environment (the Administrator, 2026-11-14): what works on the owner's NIPR computer works on every NIPR computer, PnP.PowerShell included; the owner's account has no special flag. Windows PowerShell 5.1 is the least that is always there: all engine and step code runs on it. The work-computer rounds are the 5.1 test; the cloud tests stay on PowerShell 7, and a 5.1 fault is fixed when a round finds it.

Preflight: RADE's checks are the one preflight; an app keeps a probe flow only for rights a script cannot see (for example the connector data policy, Send As). Updates: RADE compares the installed version with the newest one at each run; an app only shows its installed version.

## How an app gets the engine

The Administrator, 2026-11-15. An app repo builds alone: it needs no RADE checkout.

- The app keeps a lock file that names a RADE commit and every file the engine reads at that commit, each with its SHA-256. From engine-v36 the engine reads 42 files: `apps.json` (the one config home: the repo, the RADE page and the Teams channel name go into every bundle; fleet v2 DEC 7) and RADE's logo path in `engine/window.json` (`logo`), and the 450-line splits (fleet v2 DEC 6) add (`engine/rade_ui_text.ps1`: part 2 of the shared UI file, put into every bundle right after `engine/rade_ui.ps1`; `engine/rade_parts.py`: the part lists, engine_text and the fixed lists, moved out of rade_build.py; `engine/ps/15-restore-run.ps1`: the Restore functions, moved out of 14-restore.ps1; `engine/ps/16-site-scripts.ps1`: the sign-in block and the site scripts of the checks, moved out of 07-checks.ps1); from engine-v31 it reads 37 files (`engine/rade_fields.py`: the parts of a bundle from single manifest fields, moved out of rade_build.py; `engine/ps/14-restore.ps1`: Restore); 35 from engine-v30 (the Maintenance tools add `engine/ps/13-maintenance.ps1` and `engine/ps/window/11-tools.ps1`); 33 from engine-v29 (UI standard v1 adds `engine/rade_tokens.py`, `engine/ui-tokens.json` and `engine/fonts`: three .ttf files and OFL.txt; [ui-standard.md](ui-standard.md)); 27 from engine-v28, 26 from engine-v21, 25 from engine-v18, 24 from engine-v11 to engine-v17. The engine-v28 files: `engine/rade_build.py` (the build, Python), `engine/window.json` (the window's layout values: text column and minimum size; the build puts them into every bundle), the 22 PowerShell parts in `engine/ps/` (12-resume.ps1 from engine-v28) (the engine code every bundle carries, joined in the order of `ENGINE_PARTS` and `WINDOW_PARTS` in engine/rade_parts.py; the Administrator, 2026-11-17, docs/code-standard.md C10), `engine/rade_ui.ps1` (the shared UI file: theme tokens, builders, drawing helpers and the layout self-check; the build puts its text into every bundle, and an app window can reuse it) and `assets/logo/rho-fulcrum-128.png` (Rho Fulcrum from engine-v28: the window's logo and its title-bar icon; Rho Bold, `logo-rho-128.png`, from engine-v10 to engine-v27). An app's lock must list them all: a lock made before engine-v11 lists 3 and builds with its old engine until the app moves the lock. `python3 scripts/engine_files.py` gives the list from a trace of the engine's file opens on the sample build, not from a search: a new engine can read a new file.
- The app's build downloads those files from `raw.githubusercontent.com/rhope-ops/RADE/<commit>/<path>`, checks each SHA-256, and runs the engine with `--app-root`. A commit never changes, so the same lock always gives the same bundle.
- The app owns its lock. A RADE session never edits an app repo: it reports the new commit, and a session of the app changes the lock, rebuilds and tests. Rollback = the app keeps its old lock.
- Releases (the steps a person follows: [RELEASE_AND_HANDOVER.md](RELEASE_AND_HANDOVER.md)): after an engine change merges, a manual run of the workflow [release.yml](../.github/workflows/release.yml) from main (input: the next tag, `engine-v<N>`) runs the checks, signs the file list as a build attestation (keyless, no secret) and makes the tag and the GitHub release with `rade-engine.sha256` (the signed list, the authority) and `rade-engine.lock.json` (the same hashes in lock form). The app copies the commit and the hashes from that release into its lock and records the tag. The app's build still fetches by commit and checks the hashes; it needs no new tool. To check the signature by hand: `gh attestation verify engine/rade_build.py --repo rhope-ops/RADE`. Before each release, set `ENGINE_RELEASE` in engine/rade_build.py to the number of the new tag: every bundle carries it as `$engineRelease`, and the saved runner copy (rade-runner.ps1, the desktop shortcut's target) is replaced only by a bundle with a higher number (the Administrator, 2026-11-17).
- Before a release, RADE's checks build every application in [../apps.json](../apps.json) with the new engine (`python3 scripts/check_apps.py`, the app canary): an engine or schema change that breaks an app which builds with its locked engine fails in RADE, not later at the app's lock change. It reads a copy of each app's main branch and changes no app. It does not run the bundle: the step contract and the shared files at run time are tested with the sample app only.
- What an app repo must hold: [make-an-app.md](make-an-app.md).
- First app and working example: rhope-ops/90-161.Z `scripts/rade.lock.json`, `scripts/build_paste_bundles.py`, docs/dev-setup.md "RADE engine".

## Bundle layout

The Administrator, 2026-11-17 (docs/code-standard.md C5, C6; from engine-v11). A person reads a bundle before it runs, so:

- The header names each engine file with its own SHA-256 (`<file>, sha256 <12 hex>`): engine/rade_build.py, engine/rade_ui.ps1, engine/rade_ui_text.ps1 and every engine/ps part, so an app can match a bundle to its lock.
- The first line is the bundle hash, `# @@BUNDLE-HASH <64 hex> @@`: the SHA-256 of all the text after that line, with line ends as LF (from engine-v21; [specs/bundle-hash.md](specs/bundle-hash.md); the code is engine/rade_hash.py, one more engine file in an app's lock: 26 from engine-v21). From engine-v34 the build also writes `<bundle name>.txt`, the same bytes, for a person to open from a link (a link to a .ps1 causes problems on a gov computer; the Administrator, 2026-11-21); `--check` reports a missing or old copy as STALE. From engine-v40 the first lines after the hash line are the numbered run steps (from engine-v41 after one line "GENERATED by the RADE engine from <manifest>", so the kit code standard C6 finds the banner in the first 15 lines; 90-161.Z R43) (copy the text, open Windows PowerShell ISE, File > New, paste, F5; `RUN_STEPS` in engine/rade_parts.py; 90-161.Z R43 E1), so a person who opens the .txt sees them before the code. The build writes the same value to `<bundle>.sha256.json` beside the bundle (the app commits it with the bundle; `--check` reports a missing or old one as STALE) and prints a `HASH` line. The RADE page compares its own hash of the text with both; the bundle hashes its own text and shows `Script check: <first 12>...<last 4> (checked)` or `DOES NOT MATCH` (`Get-ScriptCheck`, engine/ps/05-installed.ps1). From engine-v35 the line ends and blank lines at the end of the text count as one LF (the ISE paste drops the final LF; [specs/bundle-hash.md](specs/bundle-hash.md) R4). Until a work-computer round proves the paste, the bundle only shows the answer.
- Paste guard (from engine-v38; the Maintainer's tool retirement plan P4a, 2026-11-23): after the header comment, all the text is one script block, `$script:PasteBody = { ... }`, and only the last line of the bundle runs it (dot-sourced, so the scope is the same). A paste that is cut short has no closing brace (a parse error: nothing runs) or ends before that line (nothing runs). The guard prints nothing. It stops no changed but complete text: that is the hash's job, which only shows its answer (above). The code is `GUARD_START` and `GUARD_END` in engine/rade_hash.py; tests/paste_guard_test.py cuts the sample bundle at about 200 spread lines and at each line of its first and last parts.
- After the header, a "Contents" list gives the line of each part, each embedded file and each engine part. Each part starts with a `# ==== Part k of n` line, each file with a `# ---- File i of n` line (its folder, name, source path and SHA-256) and each engine part with a `# ==== Engine part: engine/ps/<file> (sha256 <12 hex>)` line.
- Shared blocks: a block between `# >>> <name>: generated from ...` and `# <<< <name>` that two or more text files hold is kept once in `$shared` (part 2). Each file holds one `# @@SHARED <key>@@` line in its place, and `Write-BundleFile` puts the block back before it writes the file, so each file on the computer is the same as in the app's repository. The build checks the round trip.

## Guardrails

Decided by the Administrator, 2026-11-14. Each one stops an honest mistake; none is a security control.

| Guardrail | What RADE does | What it reads or writes |
|---|---|---|
| NIPR only | Before anything is written, RADE joins this computer's host name and its own domain into its full name and goes on only when that name contains `.area52.` (`$niprLabel` in the engine; any letter case; the Administrator, 2026-11-15). Else it prints only "This application cannot be installed in your environment." and ends: no folder, file, saved check, window or e-mail. The same test is the first check row (`nipr`, never saved). It cannot prove NIPR: a SIPR name that holds area52 passes. | Reads two local values (host name and computer domain, `IPGlobalProperties`). Contacts no host and does no DNS lookup. The name is never shown or saved. |
| Site address | Only an address that starts with the DAF SharePoint prefix (`$sitePrefix`) is accepted, so RADE never signs in to or writes to another host. | Nothing new. |
| Site rights | Unchanged: manage lists, manage the site and manage permissions (Full Control). The sign-in check also shows whether the user's own account is a site collection administrator. Shown only, never required. | Reads one flag of the user's own account. No list of administrators. |
| One install per site | An app with `marker` in the manifest (list, row key, column) keeps an install record on the site: after a deploy that reached a step, RADE writes the version and the date to that one row (with the word "partial" until every needed step has passed). In a deploy the sign-in check reads the row; any value counts. A site that has it, and an account whose own record ("Shared files") holds no step for that site: the check is FAILED and no step runs (a second import would run every flow twice). For such an app the record is kept for each site: its key ends in `@` and a short hash of the site address, never the address, so versions, step states and the made list of one site do not count on another. The row is not written when the own record could not be saved. In the window, a changed site address drops the site results shown for the old one. A row that cannot be read is FAILED too. A first install always reads the row fresh, and the plan shows a "once for each wing" notice. If the row cannot be written, the run says so. | Reads and writes one row of the app's own list. No name. |

Limits: RADE cannot see an install on another site (that needs a tenant search, which "No reconnaissance" forbids). Until the Maintenance card can repair another account's install, only the account that installed an app can update it; if that account's record file is lost or damaged, its next deploy is stopped too, and a site owner must clear the row's value by hand. A run that stops inside its first step writes no row. A renamed app has a new record key, so its installer is stopped until the row is cleared. Not verified on a device: the window's handling of a changed site address, the area52 name read, the administrator read and the row read and write on PnP.PowerShell 1.12.0 (cloud tests use a fake module, tests/fake-pnp).

## Shared files

Decided by the Administrator, 2026-11-15. The RADE page picks the app, and each app is one paste with its own engine lock, so several engine versions use `OneDrive\RADE\Config` on one computer. An engine cannot keep fields it does not know through a read and a write (PowerShell cuts data below its depth limit with no error), so no engine rewrites another app's data.

| File in RADE\Config | Holds | Written by | If it is lost |
|---|---|---|---|
| `installed\<12 hex>.json` | One app's install record: version, step states, the made list. Name = the first 12 hex of the SHA-256 of the lower-case record key. Contract: [../schemas/rade-installed.schema.json](../schemas/rade-installed.schema.json) | Only a deploy of that app | The app reads as not installed; with a site marker its next deploy is stopped ("Guardrails") |
| `rade-checks.json` | Saved checks (a cache). Contract: [../schemas/rade-checks.schema.json](../schemas/rade-checks.schema.json) | Every run of every app | A check runs again |
| `rade-checks-last.txt` | The checks of the last run, one line each with the result and the detail (masked), for a person to read; from engine-v22. It is not in a results folder, so no e-mail draft attaches it | Every run of every app (the newest replaces it) | Nothing: the next run writes it again |
| `rade-mail-to.txt` | The results address (test rounds) | A test round | The owner types it again |
| `rade-window.json` | Where the user last closed the window: bounds, state, the scale, and the client size and state at close (numbers and two words, no name or path; R28) | Every window, at close | The window opens maximized on the screen with the mouse |
| `rade-shortcut.txt` | The folder the user chose for the RADE shortcut on the install card (one line; R29 N8) | A deploy, when its install card asked for the folder | The install card offers the Desktop folder again |
| `rade-tour.txt` | That the RADE tour was shown for this Windows profile: the date, one line (R31 L6) | Every window, when the tour ends or is skipped | The tour shows one more time before Choose |

Outside Config (engine-v42; 90-161.Z R44 E1; intro-fulcrum plan step 7): `RADE\runners\<key>.ps1`, the runner copy of one app (`<key>` = 12 hex of "<app folder>/<app name>"): a copy of that app's pasted text, saved after its deploy has passed; a copy made by a higher engine release stays; a passed deploy of that app with the same or a newer engine replaces it (the PFM's Q3 answer A, 2026-11-26). Beside it: `<key>.ico` (the shortcut icon, 16, 32, 48 and 256 px, made at run time from `application.logo`, else from RADE's logo) and `<key>.lnk.txt` (the full path of the shortcut RADE made). The shortcut is named after the app's word, `application.productName` ("Kanon"), else the app name, with no version (engine-v46, the PFM, 2026-11-26; engine-v42 to v45: "<displayName> - <version>"); it starts PowerShell with `-WindowStyle Hidden`, in the folder the install card names (`rade-shortcut.txt`, else the Desktop); a new version's deploy moves the old version's shortcut to the Recycle Bin. The one runner `RADE\rade-runner.ps1` and the shortcut "RADE" of engine-v41 and before go to the Recycle Bin at the next passed deploy (only a RADE.lnk that starts that runner). If a runner copy is lost, its shortcut does nothing until the next deploy of that app.

- S1. An engine writes only its own app's record file. A file that holds a whole record with another app's key (two keys gave one file name), or that cannot be read at the moment, is not written and that app is not deployed.
- S2. A record with a schema number higher than the engine knows is not read and not written, and that app is not deployed: "a newer RADE installed this application: get the newest script from the RADE page".
- S3. `rade-checks.json` is a cache: nothing goes in it whose loss matters.
- S4. A record or cache write goes to a temporary file in the same folder, which then replaces the final file in one step.
- S5. Only a file with the exact name is read: a conflict copy that OneDrive makes is ignored.
- A change to a record that an older engine cannot read gets the next schema number (S2 then stops the older engine).

Engine-v1 (the engine in the field on 2026-11-15) kept all apps in one file, `rade-installed.json`. No deploy ran with it, so the file is not read or moved. tests/engine_test.sh runs engine-v1 and this engine on one folder ("cross-version"). A test round runs a self-test of the record functions on a scratch folder and prints 4 `PASS shared files` lines: that is the proof on Windows PowerShell 5.1. Not verified on a device: all of this section, and the file replace inside a OneDrive folder. Not tested anywhere: a record that another program holds open (no such lock on the Linux test computer).

## Modes

One engine, three modes per catalog app (`mode` in the manifest): **deploy** (install an app), **test** (a test round; the default) and **drift** (owner only). Test rounds are run by the owner only; other users only deploy (the Administrator, 2026-11-14).

## Check stages

1. **Base checks** when the window opens, before Choose: can RADE work on this computer at all (`BASE_CHECKS` in the engine). An app whose checks cannot pass is marked on the Choose screen.
2. **App checks** after an app is chosen: each step's `needs` (for example site-rights, flow-guide, pnp).
3. **Drift**: every run compares the check values with the saved baseline; the drift check app forces every check.

## Results

- No scripts in results (the PFM, 2026-11-20; R37: a collect pattern matched the .ps1 runner and the work e-mail gateway blocked the results e-mail): the collect step never copies a file with a script extension (`SCRIPT_EXTS` in engine/rade_build.py: .ps1 .psm1 .psd1 .bat .cmd .vbs .js .wsf .hta .py .sh .exe .dll .msi .lnk .scr) into the results folder and logs one line `SKIPPED script file <name> (scripts never go in results)`; the e-mail draft attaches no such file. The build fails a bundle whose collect name can match one: any name or pattern that can match a name ending in such an extension (after its last `*`, or by its fixed end). From engine-v28.
- PASSED, PASSED (fallback), WARNING, FAILED, NOT RUN. A fallback result names the documented fallback route used (for wings with less access) and counts as passed. FAILED or NOT RUN blocks a deploy (rhope-ops/90-161.Z docs/DECISIONS.md, 2026-11-14: "No deploy unless every check passes").
- Saved checks (RADE\Config\rade-checks.json; code: `$checkNoSave`, `$checkEachRun` and `$checkMaxDays` in engine/ps/08-saved-checks.ps1): NIPR, Word, disk and write run fresh every time, also again after Choose; PowerShell version, language mode and child process run once for each run of RADE (from engine-v21); every other check that passed is saved and reused for 7 days when the computer, PowerShell, PnP and the scope are the same: OneDrive, Outlook, PnP, the three network checks, site rights (CAC sign-in) and the Power Automate look-and-answer (the Administrator, 2026-11-19: keep the code, correct this sentence). "Run checks again" and the drift check run everything.

## Pause and resume

The PFM, 2026-11-20 (every app pauses and resumes when the user closes the window, removes the CAC or is stopped in any other way). Code: [../engine/ps/12-resume.ps1](../engine/ps/12-resume.ps1); tests: tests/resume_unit.ps1 and tests/resume_test.sh. From engine-v28.

- After each step ends (passed, failed, skipped, answered, interrupted), the engine writes the round state to `Rounds\<round>\rade-state.json`: schema `rade-state/1`, the round, the build (`$buildId`), the application, the time, the selected steps, each finished step (its state, its summary lines, masked as in the report, and its made list) and the log so far. The write goes to a temporary file that then replaces the file in one step (S4). A failed write is one log line; it never stops the round. A round that ends removes the file; the e-mail draft never attaches it.
- When the same round of the same build and application starts again and the file exists, the ready card offers "Resume at step N of M" (the main button) and "Start over"; text mode asks R (or Enter) to resume, S to start over. N is the first selected step that a resume runs. The state of another application of the same paste is left as it is.
- Resume keeps each step that ended (passed, failed, skipped, answered; the Administrator, 2026-11-20, docs/DECISIONS.md): its lines go back into the summary, its state counts for `after` and the round result, it does not run again. The step that was running when the run stopped (saved as INTERRUPTED: the CAC was out, or the window closed while it ran) runs again, then the steps after it. A step that needs a folder runs only when the folder is picked again. The install record never holds INTERRUPTED: it records NEEDS REVIEW. The earlier log comes back above a line `---- resumed <time> ----`. Clean-up does not run again (it could recycle what the kept steps made). Start over moves the file to the Recycle Bin and runs every step.
- A state file of another build of the round is never resumed: it goes to the Recycle Bin with the line "Saved progress of another build of this round was not used." A file that cannot be read goes there too, with "The saved progress of this round could not be read (<why>), so the round starts over."
- Disruptions: Exit or the window's X during a step asks first, as before; the run stops and the state of the last finished step stays. Windows PowerShell or ISE closed, or the computer restarted: the state of the last finished step stays. CAC removed: a step result line or error line that says the sign-in failed (`$signInLost`: smart card, "sign-in failed", "authentication failed" or "was cancelled" and the like) makes the step INTERRUPTED, not NEEDS REVIEW; the round stops there and the window shows "Insert your CAC, then select Resume." with a Resume button that runs that step again.
- Not verified on a device: the Recycle Bin move, the window's Resume and Paused cards, and a CAC removed during a real sign-in (the words Windows and PnP.PowerShell print then are not known yet).

Sign-in time (engine-v40; 90-161.Z R43 E4, the PFM, 2026-11-25; engine-v44): the rights check's detail ends with `SIGNIN seconds=<N>`, the seconds from the start of the sign-in to the end of `Connect-PnPOnline`; it shows in Details, the report and `rade-checks-last.txt`. The rights check result is saved for 7 days, so a new timed check needs "Run checks again". engine-v40 to engine-v43 also printed `watch=on|off` and read `RADE_SIGNIN_WATCH`.

No size watch (engine-v44; the PFM, 2026-11-26): RADE never touches the CAC sign-in window; it opens at its own size. The size watch of engine-v35 to engine-v43 (`Start-SignInSize`: `SetWindowPos` on new windows of the child, from a timer thread, to about 480 x 360) froze the sign-in in 90-161.Z R44 r2 (one host: watch on, 2 windows not responding at 9 s and stopped at 180 s; watch off, signed in after 5 s). It is deleted, with `Stop-SignInSize` and `RADE_SIGNIN_WATCH`. The block keeps its name and its two marker lines (`# ---- RADE sign-in window size (start` and `(end)`), so an app's build that copies it needs no change; an app script that called `Start-SignInSize` or `Stop-SignInSize` must drop those calls (or call `Connect-RadeSite`).

Sign-in stage and window state (engine-v43 S1 to S3; the PFM, 2026-11-26, after the sign-in froze in both runs of 90-161.Z R44 r1): every child script that signs in calls `Connect-RadeSite` (in the sign-in block, engine/ps/16-site-scripts.ps1), which prints `STAGE signin`, the `SIGNIN` line and `STAGE none`. RADE stops a stage that runs longer than its limit (`$signInStageSeconds` = 180 for the rights check, the install record and Restore; Back up keeps `$toolStageSeconds`) and names it, so a frozen sign-in ends with a result. While `Connect-PnPOnline` runs, `Start-SignInReport` prints a line at each change: `SIGNIN-WIN t=<s> windows=<n> owned=<n> min=<n> size=<WxH> hung=<n> front=<0|1>` (the visible windows of that child process only: no title, no text, no other process). RADE puts each SIGNIN and SIGNIN-WIN line in the run log with `host=<ise|child|shortcut|console>`; the rights check detail ends with the SIGNIN line and the host, or the last SIGNIN-WIN line when the sign-in did not finish. RADE sets `RADE_HOST` at start, so the steps it runs can read it. An app's own sign-in script can copy the sign-in block and call `Connect-RadeSite`.

## Step contract

What RADE and a step script give each other (the Administrator, 2026-11-14: the contract comes before the safe second run and the undo list). A script that does not use the contract still runs.

**RADE gives the step** (the child process):

| How | Name | Value |
|---|---|---|
| Parameter | `-Id`, `-NoPause` | The profile folder name; no pause at the end. Plus the step's fixed `args` and its `ask` folder. |
| Environment | `RADE_CONTRACT` | `1` (the contract version). |
| Environment | `RADE_MODE` | `test`, `deploy` or `drift`; `uninstall` for the app's Uninstall steps (engine-v40). |
| Environment | `RADE_MADE` | Uninstall steps only (engine-v40): the path of a JSON file (`rade-made/1`: `app`, `made`: step, kind, name) with the made list of the install record. |
| Environment | `RADE_APP`, `RADE_APP_VERSION` | The chosen app and the version this bundle installs (empty in a test). |
| Environment | `RADE_INSTALLED_VERSION` | The version now installed, or empty (deploy only). |
| Environment | `RADE_STEP_LAST` | This step's last state at this version: `PASSED`, `NEEDS REVIEW`, `SKIPPED` or empty (deploy only). |
| Environment | `RADE_SITE` | The site address from the Check screen, or empty. A step that has it must not ask for it again. |

**The step gives RADE** (one line each on standard output):

| Line | Meaning |
|---|---|
| `PASS ...`, `FAIL ...`, `SKIP ...` | One result each; the step state comes from the counts and the exit code. |
| `PROGRESS n/m` | Moves the step bar; not logged. |
| `NOW <text>` | R31 L7: what the step does now, in plain words. The window shows it on the now-doing line under the step's bar; not logged, not a result. Without it, the line shows each result line as a plain sentence: the words after `PASS`, `SKIP` or `FAIL`, after "Checked: ", "Skipped: " or "Needs review: ". The step's manifest field `doing` (1 to 80 characters, present tense) shows there when the step starts. |
| `FALLBACK: <route>` | The step used its documented fallback route (for a user with fewer rights). A step that passes this way reads PASSED (fallback) and counts as passed. |
| `MADE <kind>: <name>` | Something the step created (kind: a lowercase word such as `list`, `column`, `flow`, `file`). RADE removes any address from the name and keeps it for the undo list. The line is not a result: words in the name never count as PASS or FAIL. |

A step the user does by hand (kind `guide`) lists what it creates in the manifest field `makes`. A step may give its own help text in the manifest field `help`; RADE shows it when the step needs review. A step may give a `title` (1 to 56 characters; longer is a build WARNING): the window shows it where it would show the step name to a person (the hand step's headline, the step line of a run, the Details screen's step boxes); without one it shows the name. The log, the report, the summary, the results files and every key keep the name. In a hand step's guide, a line that starts with a number and a full stop ("1. ") is a numbered line; more than 10 numbered lines is a build WARNING ([window-design.md "Text lengths"](window-design.md#text-lengths)).

**Buttons of a hand step** (R31, the Administrator, 2026-11-19; kind `guide` only). `hide`: 1 or 2 of `done`, `failed`, `skip`: the card does not show those buttons (use it when a button leads to no different result); one button stays; text mode does not offer a hidden answer and does not take it (it asks again, 3 times at most; then the step is SKIPPED with the reason `no answer that this step offers was given`, not `by you`). A step with `answers` cannot hide `done`: its questions come after Done. `answersOnly: true`: the step has no card with Done, It failed and Skip: the window shows its first question at once. Such a step needs `answers` and has no `file`, `guide` lines, `url`, `urlConfig`, `marker`, `doneText`, `doneLog` or `hide`. Its result: PASSED (`answered by you`) when every question that shows is answered; FAILED (`reported by you`) when an answer in a question's `failOn` was given; SKIPPED in text mode (`its questions need the RADE window`), which cannot ask.

**Questions of a hand step** (manifest field `answers`, kind `guide` only; the Administrator, 2026-11-15): 1 to 4 questions `{key, prompt, kind, choices, failOn, showIf}`. `showIf` (R31 E3): `{key, in}`, the key of an earlier yes/no or pick question of the step and 1 or more of its answers; the question shows only after one of them, else its line is `  Answer <key>: not asked`. `failOn` (R31 E2; only in a step with `answersOnly`, for a yes/no or pick question): 1 or more of its answers that mean the step failed. After the first such answer the window asks "What did the error say?" (empty is allowed); the other questions are still asked; the step's line is `FAILED (reported by you) in <time>: answer <key>: <answer>. Error text: <text>`, the text masked and cut as the "It failed" text is, and the answer lines follow it. The key matches `^[a-z][a-z0-9-]{0,23}$` and is unique in the step; the prompt has 1 to 120 characters; kind `yesno` (Yes / No), `pick` (`choices`: 2 to 4 words of 1 to 40 characters; only a pick has them) or `text` (one line, 10,000 characters at most). Write the question as the first sentence; anything after it is shown as a smaller line under it. Start the prompt with the question itself; do not start with an abbreviation that ends in a full stop ("e.g. this" would make "e.g." the headline). Prompts and choices are trimmed; choices that differ only by case or spaces are rejected. After the person selects Done (not after "It failed" or Skip), the window asks each question on its own card, in order ([window-design.md "Cards"](window-design.md#cards)); their time counts into the step's time and the step state stays what Done gives it. Each answer is one line in the summary (the e-mail body) and the report, directly under the step's line: `  Answer <key>: <value>`. A yes/no or pick value is the word of the button. A text value is masked as the "It failed" text is (`ConvertTo-UserText`: the DODID, e-mail addresses as `<EMAIL>`, site addresses as `<SITE>`), kept whole (up to 10,000 characters: the box takes no more, and a paste that is cut gets a note with the count (R7); R28: an answer cut at 120 characters lost the PFM's note); an empty text is `(no text)`. Text mode asks nothing and records `not asked (text mode)`; a window closed during the questions records `not answered (the window closed)`. Nothing is saved: a run asks again. The schema check (`scripts/check_manifest.py`) and the build reject a bad list.

**Rules for a step script:** safe to run again (create only what is missing, and print `MADE` only for what this run created); when `RADE_STEP_LAST` is `PASSED`, check and do nothing if nothing changed; never print a site address, a person or an ID.

In a deploy, RADE saves each step's state, version, time and `made` list under `steps` in the app's record file ("Shared files"); a `made` list adds up over runs.
